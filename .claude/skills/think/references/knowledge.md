# 知識レイヤーと workspace ライフサイクル

`/think` を回すほど蓄積される2種類のローカル資産（`knowledge/` と `workspace/`。どちらも gitignore・会話ローカル限定）を、**整理された状態に保つ**ための規律。放置すると (1) 個人知識が未整理のまま埋もれ、(2) workspace が無限に肥大する。ここでその2つを構造で殺す。

## Contents
1. 知識の2レイヤー分離（recall規律の核心）
2. `knowledge/profile.md` の運用
3. workspaceライフサイクル（肥大の抑制）
4. 残存不確実性（この規律自体について）

---

## 1. 知識の2レイヤー分離（recall規律の核心）

CLAUDE.md 原則④「**過去結論はrecallしない**（anchoring毒）」は **テーマの結論** に対する規律であって、**rioという人物の属性** には適用しない。ここを混ぜると、再利用すべき個人文脈まで捨ててしまう。2レイヤーに明確に分ける:

| レイヤー | 置き場所 | 中身 | recall | 理由 |
|---------|---------|------|--------|------|
| **A: テーマ事実/結論** | `workspace/INDEX.md`・各 `workspace/{テーマ}/` | 検証済ソースURL・失敗クエリ・既知の罠・**当時の暫定結論** | **結論はrecall禁止**。ソース/失敗クエリのみ再利用 | 過去結論を確定扱いすると anchoring毒。毎回ゼロベースで再導出する |
| **B: rioプロファイル** | `knowledge/profile.md` | 関心領域・判断の好み・既知の制約/文脈・地雷・確定した個人事実 | **recall推奨** | 「人物の安定属性」であってテーマの真偽ではない。提案の当てはめと提示形式の最適化に使う |

**なぜ B は anchoring毒にならないか**: 「rioはスピード重視」「体制はrio+AI」を思い出しても、*調査対象トピックの真偽* をゼロベースで再導出することは妨げない。B が影響するのは「**どう当てはめ・どう提示するか**」だけで、「**何が事実か**」ではない。この線引きを守る限り B は安全かつ有用。

**やってはいけない越境**:
- B を使って「rioはXが好きだから結論もXにしよう」と **テーマの結論を歪めない**（B は提示の最適化用。真偽の根拠にしない）。
- A の過去結論を B に昇格させて確定事実化しない（テーマ結論は毎回再検証対象のまま）。

## 2. `knowledge/profile.md` の運用

### 実体化
初回のみ `references/profile-template.md` を `knowledge/profile.md` にコピーして使う（`knowledge/` は gitignore なのでコミットされない＝ rio のローカルにだけ残る）。

### 読む（Recall 時 = 事前読み込み）
`workspace/INDEX.md` の grep（レイヤーA）に加えて、**`knowledge/profile.md` を読む**（レイヤーB）。存在しなければスキップ。読んだ内容は「今回の当てはめ・提示形式の初期値」として扱い、テーマの真偽判断には使わない。

### 書く（提案完了時 = Phase 5 の INDEX 追記と同じタイミング）
そのセッションで **新たに判明した rio の安定属性** があれば `knowledge/profile.md` を更新する。ただし:

- **マージ & 重複排除**。append-onlyにしない。既存項目と突き合わせ、重複は統合、矛盾は新しい方で上書き。**同じことを二度書かない**のが肥大防止の要。
- **抽出はルールベース寄りに**（原則7①の精神）。「重要そう」で何でも書かない。書いてよいのは:
  - rio が明示的に述べた好み/制約/地雷（例:「表より結論先出しがいい」「その工数の話は設計で」）
  - rio が繰り返し選ぶパターン（2回以上観測 = 恒常的傾向として記録可）
- **推測を書かない**。1回の発言から人格を決めつけない。不明は空欄のまま。
- 追記してよいのは「更新ログ」節のみ（何をマージ/修正したかの1行）。本体はマージ運用。

### 越境の禁止（再掲）
profile は「提案の当てはめ」と「提示形式」のためだけに使う。**テーマの結論の根拠にしない**。

## 3. workspace ライフサイクル（肥大の抑制）

`/think` 実行ごとに `workspace/{テーマ}/` が増え、raw中間物（research.md / analysis.md）が永久に残る設計だった。これに寿命を与える。

### 原則: 「昇華済みなら raw は剪定してよい」
1テーマの価値は最終的に次の3つに **昇華** される:
- `workspace/INDEX.md` の1行（検証済ソースURL・失敗クエリ・既知の罠）
- 最終成果物（`proposal.md` / `design.md`）
- （個人属性があれば）`knowledge/profile.md`

昇華が済めば、raw中間物（`research.md` / `analysis.md` / `repo-analysis.md`）は **圧縮アーカイブに退避**してよい。完全には消さない（次回 recall の一次ソースになり得る）が、live な workspace には残さない。

### サイズバジェット（Anthropic 準拠）[G1]
Anthropic は「常時ロードするメモリ」に明確な数値上限を置いている。これに倣う:
- **Claude Code auto memory**: `MEMORY.md` は**先頭200行/25KBのみ**毎回ロード。超過分はロードされない。
- **CLAUDE.md**: **200行超で adherence 低下**。詳細はトピックファイルへ分割。
- **Agent Skills**: `SKILL.md` は5,000トークン未満推奨（progressive disclosure）。
- 出典: [Claude Code memory](https://code.claude.com/docs/en/memory) / [Agent Skills](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview)

**本ハーネスへの適用**:
- `knowledge/profile.md` は **200行/25KB を目安上限**にする。超えたら**マージ&重複排除で簡潔化**（自動削除はしない＝情報損失防止。`compact-workspace.sh` は警告のみ出す）。
- `workspace/INDEX.md` は **エントリ数に上限**（既定150件）。超えたら古いエントリを `workspace/INDEX-archive.md` へ退避（下記ローテーション）。

**注意（実測との乖離・未解決）**: INDEX.md は MEMORY.md と違い**毎回全ロードされず grep される**ので、25KB バジェットをそのまま当てはめるのは誤り。ただし実測（2026-07-16）で **36エントリ / 132KB＝1エントリ平均約3.6KB** と肥大しており、**150件上限に達すると約520KB**になる。grep のヒット1行がそのまま context に載るため、効く制約は「ファイル全体のバイト数」ではなく **1エントリの長さ**。現状の150件上限はバイト肥大を抑える機能を実質果たしていない。`compact-workspace.sh` は 100KB 超で警告を出すが、**1エントリを短くする規律は未整備**（rio 判断待ち）。

### バジェット（テーマ単位の目安）
- **1テーマ = 最終成果物 + INDEX 1行** を live に残す。raw は N日（既定30日）経過でアーカイブ。
- workspace 全体が肥大したら（体感で重い/検索が遅い）コンパクションを実行する。

### INDEX ローテーション [G2]
`INDEX.md` は1テーマ1行で**無限に増える**（per-theme dir は剪定してもINDEXは残る）。Claude Code の「索引を簡潔に保ち詳細はオンデマンド」に倣い、上限超過分を退避する:
- `compact-workspace.sh` が `INDEX.md` の**実エントリ数**（`- [テーマ] (YYYY-MM-DD, workspace/{dir}/) …` 形式の行のみ。recall規律ヘッダやフォーマット例は数えない）> 上限（既定150）を検出すると、**日付が古いエントリを `workspace/INDEX-archive.md` へ移動**。`INDEX.md` は最新N件に保つ。
- **「古い」は日付で判定する（位置ではない）**: 実INDEXは prepend/append が混在しており出現順が日付順になっていない（実測: 昇順違反4件・降順違反14件）。位置で切ると最新エントリを退避しかねない。
- **退避であって削除ではない**（Zep の invalidate-not-delete に倣う）。`INDEX-archive.md` も **recall 時に grep 対象**（一次ソースとして生き続ける）。
- これで「毎回読むINDEXは軽いまま」「過去の失敗クエリ/ソースは grep で辿れる」を両立する。

### コンパクション手順（ローカルで実行）
`scripts/compact-workspace.sh` を使う（既定 dry-run・`--apply` で実行）。動作:
1. `workspace/*/` を走査し、mtime が N日以上前のテーマを対象にする。
2. 対象テーマを **丸ごと** `workspace/_archive/{テーマ}.tar.gz` に圧縮退避（**何も失わない**・完全復元可能）。
3. live 側には最終成果物（`proposal.md` / `design.md`）と `.compacted`マーカー（アーカイブ位置を記録）だけ残し、raw中間物を削除。成果物が無いテーマ（Understand止まり等）は最新の1ファイルをstubとして残す。
4. **ガード**: `workspace/INDEX.md` に当該テーマの行が無ければ「昇華未完」と見なしスキップ + 警告（recall索引に載る前に消さない）。
5. 圧縮前後のサイズを報告。

詳細な安全策はスクリプト冒頭のコメント参照。**このスクリプトは rio のローカル（実 workspace がある環境）で走らせる**。リモート実行コンテナは fresh clone で workspace が空なので対象が無い。

### やってはいけないこと
- INDEX.md への昇華（レイヤーA）を済ませる前に raw を消さない。
- アーカイブ（`_archive/`）を消さない（recall の一次ソース）。消すのは live の raw のみ。
- コンパクションで最終成果物（proposal/design）を消さない。

## 4. 残存不確実性（この規律自体について）
- profile への「2回観測で恒常傾向」の閾値は経験則で、恣意性が残る。誤って地雷を刻む/外すことはあり得る → rio が profile.md を直接編集できる前提を維持する（人間が最終編集者）。
- コンパクションの「N日」「昇華済み判定」はヒューリスティック。ガード（INDEX行チェック・完全アーカイブ）で不可逆な損失は防ぐが、判定ミスで live から早く消える可能性はある（アーカイブから復元可）。
