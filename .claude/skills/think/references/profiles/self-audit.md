# self-audit — 自リポジトリ実査プロファイル

**対象**: 自分のリポジトリ・設定・ハーネスを調べて直す問い（実測: workspace 164テーマ中 **35件 / 21%**）。
例: `think-harness-*`, `harness-engineering`, `ai-dev-template-*`, `persona-android-harness`, `anotherball-skills-audit`

**なぜ専用プロファイルか**: 一次ソースが**外部Webではなく自分のコード**であるにもかかわらず、現行ハーネスの情報収集ソースは全てWeb/SNSのMCPで、ローカル実査の手順が定義されていない。
また現行の入力分類（`SKILL.md` の「GitHub URL → リポジトリ分析モード」）は**URLを伴わない自リポ実査を拾えず**、Web/SNS収集パイプラインに流れてしまう。

## ダイヤル（`_shared.md` からの差分のみ）

| パラメータ | 値 | 理由 |
|---|---|---|
| `primary_source` | **local-repo（file:line 必須）** | 真実はコードにある。ドキュメントは二次ソース扱い |
| `collection_shape` | **mechanical-extraction-then-execute** | 機械抽出で全数を出し、実行で確かめる |
| `min_sources` | 1（ただし**実証必須**） | 自リポは一次ソースが1つしかない。代わりに「実行して確かめたか」を要求する |
| `verification_mode` | **execute-to-confirm** | cross-model より「実際に動かす」が強い証拠 |
| `divergence_count` | **0** | 発散より発見の網羅性が価値。ただしrioが求めれば有効化 |
| `rubric_id` | **self-audit** | judge層2で Precision / 実証率 / 再現手順 を見る |
| `default_endpoint` | Decide | |

## 手順

### 1. 機械抽出（LLMに「重要そうな箇所」を選ばせない）

対象を**規則で全数抽出**する。原則7①（ルールベース抽出）をコードに適用する。

```bash
# 参照パスの実在確認（設定が指すファイルが本当にあるか）
grep -ohE '(\.claude/[A-Za-z0-9_./-]+|references/[^ ]+\.md|scripts/[^ ]+\.sh)' <対象> | sort -u | while read p; do
  [ -e "$p" ] && echo "OK   $p" || echo "MISSING  $p"; done

# 宣言と実体の突合（設定に書かれたツール/エージェント名が実在するか）
grep -ohE 'mcp__[a-z0-9-]+' <対象> | sort -u
```

抽出の観点（最低限）:
- **宣言と実体の乖離**: 設定が参照するファイル・ツール・エージェントは実在するか
- **自己矛盾**: そのファイル自身が課している制約を、自分が破っていないか
- **死んだ設定**: 撤去したはずのものへの許可・残骸が残っていないか
- **サイズ制約**: 公式に上限がある項目（例: SKILL.md 500行）に対する現在値

### 2. 実行して実証する（★このプロファイルの核心）

**静的に読んで得た結論は「推論」であり「実証」ではない。** 実行できるものは実行する。

| やったこと | 得られる主張の強さ |
|---|---|
| ファイルを読んで「壊れていそう」 | **推論**（inferred） |
| 実際に起動して落ちるのを見た | **実証**（confirmed） |
| 落ちた原因を特定し、修正して動くのを見た | **実証＋修復可能性の確定** |

**実例（このプロファイル自身の由来）**: `grok-mcp` を「読んで壊れている」で止めず実行し、`AttributeError` を実測。さらに依存を `mcp<2` に固定して `Ready.` まで起動を確認し、**「永久に使えない」という当初の推論が誤り**だと判明した。読むだけで止めていたら誤った結論を出していた。

### 3. 推論と実証をラベルで区別して書く

成果物には各所見に **[実証]** / **[推論]** を付す。混ぜない。

```
[実証] uvx grok-mcp は AttributeError で起動しない（2回再現）
[実証] mcp<2 に固定すると Ready. まで起動する
[推論] 上流が7ヶ月更新されていないため、当面この回避策が必要
```

## 既知の失敗モード（対策込み）

外部調査で確認された、コード監査の失敗モード:

| 失敗モード | 対策 |
|---|---|
| **findings are inferred, not confirmed**（ランタイム文脈がないため推論止まり） | §2 の実行を必須にする |
| **非決定的**（同じコードを2回調べて別の結果） | 機械抽出（grep/script）を使い、LLMの読解に依存しない。**再現手順を必ず残す** |
| **位置特定が不正確**（行・列を取り違える） | file:line を機械抽出で得る。目視で書かない |
| **shared blind spots**（自分が学習したパターンの問題を見逃す） | チェック観点を事前に列挙してから当てる（発見的に探さない） |
| 静的解析単独の false positive | 抽出結果を**そのまま報告せず、実行または一次ドキュメントで確認**してから報告 |

**誤検知の記録も残す**: 「バグだと思ったが設計通りだった」項目を成果物に明記する（Precision を測るため。judge層2の `Precision` はこれを見る）。

## 検証者の制約（重要）

judge agent は現行 `tools: WebFetch, Read` であり **Bash を持たない**。
したがって judge は「実証されたか」を**独立には確かめられず、著者の報告を採点するだけ**である。
→ self-audit の成果物には**再現コマンドをそのまま貼る**こと。judge と rio が自分で実行できる形にする。

## 報告のしかた

- 所見は「確定バグ」「構造的不整合」「**誤検知だったもの**」の3つに分けて報告する
- 各所見に file:line と再現コマンドを添える
- 「〜と思われる」で終わる所見は、実行して確かめるか、**[推論]** ラベルを付けて残す
