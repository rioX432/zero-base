## 設計原則（反論検証で確定）

1. **検証対象をLLMに「重要だから」で選ばせない** — 非決定的でバイアスする。**ルールベースで機械抽出**する。
2. **独立性はモデル系統でなくorigin系統で判定する**（★2026-08-23改訂・[EVAL-004](../evals/EVAL-004-cross-model-shared-origin.md)）— 同一モデルのN回多数決が独立でないのは自明だが、**異なるモデルに同じ調査をさせても、同じ検索結果・同じ二次情報源に収束すれば独立ではない**（実例: viral-loc-indie-benchmarkでGemini/Codex両方が同じ業界ブログ群に依拠し「クロスプラットフォーム80%」という誤りで一致した）。独立性は**origin_id**（発行主体＋原レポート/データセット＋版・日付）が異なるかで判定する。3モデル・5記事が同じ調査を参照していても「1 origin」。cross-modelは一次ソース発見の補助・解釈の多様性確認・反証仮説の生成に用いる**補助的シグナル**であり、それ単体を独立性の根拠にしない。
3. **最終検証者は人間（rio）に固定** — 検証の入れ子は必ず人間で止める。無限ループ禁止。
4. **結論はrecallしない** — 過去結論の呼び戻しはanchoring毒。ソースと失敗クエリのみ再利用。
5. **「検証済み」と「残存不確実性」を常にセット表示** — 検証ラベルは過信を生む。不確実性も可視化する。

## P1. ルールベース claim 抽出（G1）

研究結果(research.md)から、以下に該当する文を**機械的に全抽出**する。LLMの「重要度判断」を介さない。

抽出ルール（いずれか該当で検証対象）:
- **数値・割合・順位**: 「90%」「3倍」「#1」「$5/月」等
- **固有名詞＋断定**: 「XはYを買収した」「AはBに対応している」
- **因果・比較の断定**: 「AだからB」「AはBより速い」
- **日付・実績**: 「2026年2月に廃止」「ECAI 2025採録」

抽出後、各claimに「単一ソース / 複数ソース」を付与。**単一ソースかつ提案の根拠になるもの**を優先検証する。

### 裏取り本数の必須化（Phase 0実測で最優先と判明）

過去調査の実測では**単一ソース率93%**が最大の弱点だった（NOT_ALIGNEDは0%）。よって:
- **提案の根拠・結論を支える主張は、単一ソース禁止**。**最低2本の独立した origin**（下記）による裏取りを必須とする。
- 2本目が取れない場合は**「裏取り不足（単一ソース）」と明示**し、確定事実として書かない・提案の主柱にしない。
- 「複数ソース」は**origin独立性が条件**。同一記事の引き写し・同一一次情報の二次転載・**異なるモデルが同じ検索結果に収束しただけのもの**は1本と数える（★モデルを変えれば2本目になる、ではない）。

### origin_id による独立性判定（★2026-08-23改訂）

重要な数値claim（採用率・市場シェア・売上・ランキング等）は、以下の手順で正規化してから独立性を判定する:

1. **claimをタプルに分解**: 数値・指標名・分母（対象母集団）・地域・調査期間・公表日
2. **origin_idを特定**: 発行主体＋原レポート/データセット＋版・日付。二次記事は必ず遡って一次発行元を特定する
3. **タプル全体が一致して初めてALIGNED**（数値だけ一致・分母や時点が違う場合はNOT_ALIGNEDまたはPARTIAL）
4. 同じorigin_idを参照する記事・モデル回答は、何件集まっても**1本の裏取り**として扱う
5. **一次成果物（公式レポート・原データ・論文本文・仕様書・法令）を直接取得することを、重要claimの必須の前段とする**。検索要約やリダイレクト先の抜粋だけでは未検証扱い

## P2. claim 検証（CoVe方式 + cross-model）

各検証対象claimについて:

### Step 1: ソース内容を先に要約（CoVe第3ステップ）
WebFetch でソースURLを取得し、**主張を伏せた状態で「このページは何を述べているか」を先に要約**する。主張に引きずられないため。

### Step 2: 突合判定
要約と元の主張を突き合わせ、以下に分類:
| 判定 | 意味 |
|------|------|
| ALIGNED | ソースが主張を明確に支持 |
| PARTIAL | 関連するが一部のみ支持 |
| **NOT_ALIGNED** | URLは生きているが内容が主張を支持しない（＝grounded hallucination。最重要検出対象） |
| DEAD | URL到達不能 |
| UNVERIFIABLE | 認証要等。理由明記 |

### Step 2.6: scope check（過剰主張の検出・Phase 0で33%）

PARTIAL（URLは本物で関連するが主張がソース範囲を超過）が実測で33%と最多だった。突合時、**主張に含まれる細部を1つずつソースと照合**する:
- 数値・割合・順位・日付・固有名詞・「世界1位」等の最上級が、**ソースに明記されているか**を個別確認。
- ソースが topic は支持するが**特定の細部を支持しない場合は PARTIAL**とし、その細部を主張から削るか別ソースで裏取りする。
- 例（実測）: 「100%Claude製」「Steam世界1位」「Slack含む」はソース未記載 → 削除/裏取り対象。

### Step 3: 一次ソース直接確認＋cross-modelは補助（★2026-08-23改訂）

提案の根拠になる重要claim・数値は、**モデル一致でなく一次ソース到達で確度を作る**:

1. **まず一次成果物を直接WebFetchする**（公式統計・原データ・仕様書等）。これが最も強い証拠。
2. cross-model（`mcp__gemini-deepsearch__deep_search` / `mcp__codex__codex` 等）は**URL発見範囲の拡大・曖昧な一次資料の解釈比較・反証仮説の生成**に使う。異モデルの「回答文」自体を証拠として数えない。
3. 判定はorigin_idベースで表現する:
   ```
   証拠状態: PRIMARY_DIRECT（一次を直接確認） / SECONDARY（二次記事経由・未直接確認）
   取得状態: どのツールが発見したか（Gemini/Codex/WebSearch等）
   解釈状態: cross-model convergence（複数モデルの解釈が一致、ただし証拠ではない）
   残存不確実性: 発行元バイアス・母集団の外挿不可能性 等
   ```
4. 「PRIMARY_DIRECT＋独立origin 2本」の方が「3モデル＋同じ検索要約」より強い、という優先順位を明記する。
5. 同一モデルでN回回すのは独立性が偽物なので**しない**（この点は変更なし）。

## P3. Synthesis の cross-model 検証（★2026-08-23改訂: 多数決でなく競合仮説）

Phase 4 の本質抽出は1回勝負にしない。ただし「一致=正しい」という多数決ロジックは採らない（同じ材料を渡した一致は解釈の収束であって真実性の証拠ではなく、一致点だけを採ると無難な共通項に縮退し少数派だが重要な洞察を落とす）:

1. メインAgent(Claude)が本質案を**根拠付きで**出す。
2. **異なるモデル**（Gemini/Codexのいずれか）に**同じ材料**で本質を出させる。ChatGPT web MCPは撤去済みのため使わない。
3. Claude案と異モデル案を**競合仮説として両方保存**する（どちらか一方を消さない）。
4. 一致点・相違点・各仮説を支持/反証する証拠を列挙する。
5. **本質はモデル投票でなく証拠適合度（どちらがより多くの検証済みclaimと整合するか）で選ぶ**。
6. 合意が得られた場合も「一致=正しい」でなく「解釈頑健性が高い」とだけ表現する。不一致は「論争あり」と明記し人間に上げる。
7. フレームワーク(thinking-frameworks.md)のレンズ違いでも相違が出たら、相違自体を洞察として記録。

## P4. judge 品質ゲート（G5）

**Phase 5.1（提案）の完了時**に、`judge` agent で採点（0.0–1.0）（★2026-08-23修正: 以前「各Phase完了時」としていたが、SKILL.mdの実際の運用（Phase1-4では実装難度で刈らない=judgeを収束ゲートとして使わない）と矛盾していた。judgeは収束フェーズ限定）。**Phase D（設計）の品質ゲートはjudgeでなくCodexとのクロスバリデーション**（`phase-design-ship.md` D.2-D.3）が担う。judgeとCodex検証を二重にかけない。**judge は評価器であって判定者ではない**（合否は呼び出し側が決める）。

**層1: 証拠ゲート（常時適用・注入不要）**
| 指標 | 観点 |
|------|------|
| grounding | 主張がソースで支持されるか |
| citation accuracy | URLが実在し主張に対応するか（**arXiv ID/DOIはIDとタイトルの対応を1件ずつ実在確認**） |
| scope discipline | 数値/固有名詞/最上級がソース範囲内か |
| source sufficiency | 裏取り本数と「未裏取り」の明示 |

**層1の veto**（★2026-08-23改訂・`judge.md`と同期）: 以下が1件でもあれば、平均点にかかわらず `veto: true`。**致命的欠陥を平均で相殺しない。**
- 捏造された引用（存在しないURL/ID/論文）
- **成果物が読者に対して真として提示しており、撤回・隔離されていないmaterial claimに、NOT_ALIGNEDがある場合**（本文・背景・比較表・詳細データ内も含む。「結論・提案の根拠」に限定しない）
- 「単一originを主柱にし、明示もない」場合

**vetoの対象外（誤検知しないこと）**: 成果物自身が「この主張はNOT_ALIGNEDだった」「この数値は裏取り不足のため主柱にしない」と**透明に開示・撤回済み**の箇所は、たとえ本文にNOT_ALIGNEDという語が残っていてもveto対象にしない。

**層2: 成果評価（呼び出し側が `rubric_id` を注入した場合のみ）**
問いの種類に応じた成果軸を注入する。事実レポートと提案では評価軸が別系統である（前者=faithfulness/citation中心、後者=novelty/impact中心）ため、**層1を層2で置き換えてはならない**（置き換えると「想像力豊かだが捏造された提案」が高得点を取る）。

**減点軸にしないもの**: 実装難度・工数・ownership・保守（原則8）。「実現可能性」は成果物の記載事項であって judge の減点軸ではない。

判定バイアス対策（[arXiv:2406.07791](https://arxiv.org/abs/2406.07791)）:
- **順序入替で2回採点**（提示順バイアス検出）。ただし**同一agentの2パスは真に独立ではない**（2回目は1回目にアンカーされる）。self-preference や scale collapse には効かないので、独立性が要る場面では**別モデルファミリのjudgeを併用**する。
- **棄権("判定不能")を許容**。曖昧を無理に通さない。棄権した指標は**分母から除外**し件数を明記。
- **閾値は judge に渡さない**（threshold anchoring でスコアが閾値付近に凝集するため）。judge はスコアと観察のみ返し、合否を述べない。

### 停止条件（人間トリガー・必須）
- **合否の閾値は呼び出し側（メインagent）が保持する**。judge のプロンプト・参照文書には数値を書かない。
- 呼び出し側の閾値を下回る採点が **2回連続** → **rioに確認を上げる**（自動ループを続けない）。
- ループバック上限 **2回**。超えたら人間判断に委ねる。
- **初回スコアと改訂後スコアを分けて記録する**（張り付きが anchoring 由来か revise-until-pass 由来かを後から切り分けるため）。
- 「最終検証者は人間」。AI内の検証入れ子はここで止める。

## P5. 残存不確実性の併記（必須）

research.md / proposal.md で「検証済み」と書く箇所には、**必ず残存不確実性をセットで書く**:
```
✅ 検証済み（ALIGNED, cross-model一致） / ⚠️ 残存: 提供元バイアスの可能性・本文PDF未確認 等
```
検証の成功は信頼度を上げるが、**過信の注入を防ぐため不確実性を消さない**。

## P6. 定期ベースライン計測（measure-first）

四半期に1回、または大きな改修前に:
- 過去 `workspace/*/research.md` から claim を15件ランダムサンプリングし P2 で検証。
- NOT_ALIGNED率 / DEAD率 / 単一ソース率を実測し、本プロトコルの閾値・優先度を見直す。
- **設計を一般論でなく自分の実測で駆動する**（counter-argument 盲点2への対応）。

### ベースライン記録
| 計測日 | n | ALIGNED | PARTIAL | NOT_ALIGNED | DEAD | 単一ソース率 | 主因 |
|--------|---|---------|---------|-------------|------|------------|------|
| 2026-06-28 | 15 | 60% | 33% | 0% | 0% | **93%** | 過剰主張(PARTIAL)＋単一ソース依存。grounded hallucination(NOT_ALIGNED)は0 |

→ この実測により本プロトコルは「裏取り本数の必須化(P1)」と「scope check(P2 Step2.6)」を最優先に位置づけた。次回計測で単一ソース率の改善を確認する。
