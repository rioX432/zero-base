# Verification Protocol — 非決定性・ハルシネーション抑制プロトコル

`/think` の品質ゲート。反ハルシネーション最新研究と、自己反論検証(counter-argument)の指摘を反映した実装規律。
出典: research.md / analysis.md / proposal.md（`workspace/think-harness-modernization/`）。

## 設計原則（反論検証で確定）

1. **検証対象をLLMに「重要だから」で選ばせない** — 非決定的でバイアスする。**ルールベースで機械抽出**する。
2. **検証者は被検証者と別系統に** — 同一モデルのN回多数決は系統的バイアスを消せない。**cross-model**で独立性を作る。
3. **最終検証者は人間（rio）に固定** — 検証の入れ子は必ず人間で止める。無限ループ禁止。
4. **結論はrecallしない** — 過去結論の呼び戻しはanchoring毒。ソースと失敗クエリのみ再利用。
5. **「検証済み」と「残存不確実性」を常にセット表示** — 検証ラベルは過信を生む。不確実性も可視化する。

---

## P1. ルールベース claim 抽出（G1）

研究結果(research.md)から、以下に該当する文を**機械的に全抽出**する。LLMの「重要度判断」を介さない。

抽出ルール（いずれか該当で検証対象）:
- **数値・割合・順位**: 「90%」「3倍」「#1」「$5/月」等
- **固有名詞＋断定**: 「XはYを買収した」「AはBに対応している」
- **因果・比較の断定**: 「AだからB」「AはBより速い」
- **日付・実績**: 「2026年2月に廃止」「ECAI 2025採録」

抽出後、各claimに「単一ソース / 複数ソース」を付与。**単一ソースかつ提案の根拠になるもの**を優先検証する。

---

## P2. claim 検証（CoVe方式 + cross-model）

各検証対象claimについて:

### Step 1: ソース内容を先に要約（CoVe第3ステップ）
WebFetch でソースURLを取得し、**主張を伏せた状態で「このページは何を述べているか」を先に要約**する。主張に引きずられないため。

### Step 2: 突合判定
要約と元の主張を突き合わせ、以下に分類:
| 判定 | 意味 |
|------|------|
| ALIGNED | ソースが主張を明確に支持 |
| PARTIAL | 関連するが一部のみ支持 |
| **NOT_ALIGNED** | URLは生きているが内容が主張を支持しない（＝grounded hallucination。最重要検出対象） |
| DEAD | URL到達不能 |
| UNVERIFIABLE | 認証要等。理由明記 |

### Step 3: cross-model 独立検証（重要claimのみ）
提案の根拠になる重要claim・数値は、**Claude本体以外のモデルで独立に再検証**する:
- `mcp__gemini-deepsearch__deep_search` / `mcp__chatgpt__chatgpt_send_and_get_response` / `mcp__codex__codex`
- Claudeの判定と異モデルの判定が**一致 → 確度高**、**不一致 → 「論争あり」と明記**し人間に上げる。
- 同一モデルでN回回すのは独立性が偽物なので**しない**。

---

## P3. Synthesis の cross-model 合意（G2）

Phase 4 の本質抽出は1回勝負にしない:
1. メインAgent(Claude)が本質案を出す。
2. **異なるモデル**（Gemini/ChatGPT/Codex のいずれか）に同じ材料で本質を出させる。
3. **一致点＝本質**として採用、**相違点＝「不確実」**と明記。
4. フレームワーク(thinking-frameworks.md)のレンズ違いでも相違が出たら、相違自体を洞察として記録。

---

## P4. judge 品質ゲート（G5）

各Phase完了時、`judge` agent でルーブリック採点（0.0–1.0）:
| 指標 | 観点 |
|------|------|
| factual accuracy | 主張がソースで支持されるか |
| citation accuracy | URLが実在し主張に対応するか |
| completeness | 調査軸の漏れ |
| source quality | 一次/二次・信頼度 |

判定バイアス対策（[arXiv:2406.07791](https://arxiv.org/abs/2406.07791)）:
- **順序入替で2回採点**（提示順バイアス検出）。
- **棄権("判定不能")を許容**。曖昧を無理に通さない。

### 停止条件（人間トリガー・必須）
- judgeスコア < 0.7 が **2回連続** → **rioに確認を上げる**（自動ループを続けない）。
- ループバック上限 **2回**。超えたら人間判断に委ねる。
- 「最終検証者は人間」。AI内の検証入れ子はここで止める。

---

## P5. 残存不確実性の併記（必須）

research.md / proposal.md で「検証済み」と書く箇所には、**必ず残存不確実性をセットで書く**:
```
✅ 検証済み（ALIGNED, cross-model一致） / ⚠️ 残存: 提供元バイアスの可能性・本文PDF未確認 等
```
検証の成功は信頼度を上げるが、**過信の注入を防ぐため不確実性を消さない**。

---

## P6. 定期ベースライン計測（measure-first）

四半期に1回、または大きな改修前に:
- 過去 `workspace/*/research.md` から claim を15件ランダムサンプリングし P2 で検証。
- NOT_ALIGNED率 / DEAD率 / 単一ソース率を実測し、本プロトコルの閾値・優先度を見直す。
- **設計を一般論でなく自分の実測で駆動する**（counter-argument 盲点2への対応）。
